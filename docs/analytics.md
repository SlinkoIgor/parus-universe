# Статистика игры

Используется [Umami](https://umami.is/), бесплатная открытая аналитика на своём
сервере, без платного тарифа и лимита событий со стороны сервиса. Нужны ресурсы
существующего VPS и место под PostgreSQL. Игра остаётся статической; недоступная
аналитика не мешает загрузке, сохранению и полётам.

## Что считается

Игрок — случайный ID в `localStorage`, общий для повторных заходов в этом
браузере на этом адресе. Он передаётся как Umami Distinct ID с первого события.
Это приблизительное число браузеров, а не установленных личностей: другой
браузер, устройство, приватный режим или очистка хранилища создают нового игрока.
Без доступного хранилища ID живёт только до закрытия страницы.

«Миссия» учитывается на двух уровнях: экспедиция от Солнца до сброса и квест
из панели квестов. У каждого события есть `expedition_id`, `expedition_number`
и `visit_id` (открытие страницы); у участка полёта — `flight_id` и номер старта
в экспедиции. Автоматические участки маршрута считаются самостоятельными
перелётами. Простая перезагрузка страницы не создаёт новый старт или экспедицию.
Отмена полёта не откатывает статистику уже совершённых действий.

| Событие | Что показывает |
| --- | --- |
| `game_opened` | Заходы, повторные игроки, исходная тема, восстановление в полёте |
| `play_started` | Первый успешный запуск полёта этим браузером: кто начал играть |
| `expedition_started` | Новая экспедиция, включая подтверждённый сброс |
| `expedition_resumed` | Продолжение ранее наблюдавшейся экспедиции |
| `expedition_observed` | Первое наблюдение уже существовавшего сохранения |
| `expedition_ended` | Сброс; итоговые счётчики экспедиции |
| `flight_started` | Успешный старт участка, цель, тип объекта, способ разгона, расстояние в св. годах |
| `flight_resumed` | Восстановление активного участка, без нового старта |
| `flight_finished` | Прибытие, пролёт (`flyby`) или остановка вне цели (`stopped_short`) |
| `flight_cancelled` | Отмена или сброс во время полёта |
| `object_card_opened` | Показ большой карточки; объект, класс и открытие в полёте |
| `theme_changed` | Переход `from_theme` → `to_theme`; начальное применение темы сюда не входит |
| `quest_started`, `quest_progress`, `quest_completed` | Начатые и пройденные квесты, число зачтённых этапов |
| `active_time` | Прибавка `seconds` реального активного времени |
| `session_summary` | Накопленные счётчики экспедиции и время текущего захода при уходе со страницы |
| `runtime_error` | Тип ошибки JavaScript, до пяти на страницу, без текста и стека |

Повторная отрисовка уже открытой карточки того же объекта не прибавляет показ.
Закрытие и новое открытие прибавляет; автоматический показ истории квеста тоже
является показом карточки. Начатый полёт учитывается даже после последующей
отмены. `flight_finished` включает неудачные остановки: для успешных прибытий
фильтровать `outcome=arrived`, для пролётов — `outcome=flyby`.

Активное время собирается каждые 30 секунд: видимая вкладка с вводом за
последнюю минуту либо с выполняющимся полётом. Пауза без ввода, скрытая вкладка
и сон компьютера не накручивают время. Это реальные секунды, не годы симуляции.

Не суммировать `session_summary` и `expedition_ended` между собой: это снимки
накопленных счётчиков. Для количества действий считать соответствующие события;
для времени суммировать `active_time.seconds`. По ID экспедиции можно смотреть
все её действия и число стартов/завершений. Итоговый снимок содержит число
перелётов, отмен, карточек, смен темы и активные секунды.

## Панель и ответы на вопросы

В Umami открыть сайт **ПАРУС** и выбрать период:

- Общий счётчик Visitors Umami зависит от визитов, IP и ротации соли сервиса;
  для постоянных игроков использовать Distinct ID и сводный отчёт ниже.
  `play_started` показывает первые старты. Чтобы увидеть всех летавших за
  период, включая вернувшихся, использовать `flight_started` и `flight_resumed`.
- Событие `expedition_started` — сколько новых экспедиций начали. Группировка
  данных события по `expedition_id` и фильтр по Distinct ID связывают их с игроком.
- Событие `flight_started`, фильтр `expedition_id` — число перелётов в миссии;
  `flight_finished` и `outcome` — сколько завершили и как.
- `object_card_opened` — общее число показов; данные `object_id` / `object_kind`
  показывают популярные объекты и классы.
- `theme_changed`, данные `to_theme` — какие темы выбирают; `from_theme` — откуда
  переходят. Тема при входе находится в `game_opened.theme`.
- `quest_completed.quest_id` — какие квесты проходят; сравнение с `quest_started`
  показывает, где теряют интерес. Umami Funnels позволяет собрать воронку
  «заход → старт → прибытие → завершение квеста».

Готовый [сводный SQL-отчёт](../deployment/analytics/report.sql) считает игроков
по `distinct_id`, объединяя визиты при смене IP, и выдаёт JSON: общие числа,
игроки, перелёты и карточки по каждой экспедиции, выбранные темы и квесты.
Он только читает PostgreSQL, не требует ещё одного сервиса:

```sh
cd /srv/parus/analytics
docker compose exec -T db psql -X -qAt -U umami -d umami -v ON_ERROR_STOP=1 < report.sql
```

Период можно ограничить аргументами `-v since=2026-11-01T00:00:00Z`
и `-v until=2026-12-01T00:00:00Z` (конец не включается). Без аргументов
учитывается вся собранная история. `players_observed` — все замеченные браузеры,
`players_flew` — браузеры с запуском или восстановлением полёта за период.
При ограничении периода счётчики экспедиции относятся к этому периоду;
`start_observed=false` означает, что её начало не попало в выборку.

У старых сохранений статистика начинается с момента подключения. Старые
перелёты не восстанавливаются по ограниченному игровому журналу. Первый
наблюдаемый активный полёт помечен `observed_mid_flight`, его номер может быть
неизвестен. Количество стартов за период не обязательно равно завершениям за
этот же период: полёт мог начаться раньше. Незавершённая экспедиция не имеет
события «пройдена»: в свободной игре нет такого финального условия.

Доставка событий — best effort через `fetch` с `keepalive`. Закрытие процесса,
блокировщик или отсутствие сети могут потерять события. Повторных отправок нет:
API Umami не удаляет дубликаты автоматически. Это продуктовая статистика,
а не транзакционный журнал. Одновременная игра в нескольких вкладках также
может давать расхождения накопленных браузерных счётчиков.

## Приватность и локальная разработка

`analytics-config.js` разрешает только публичный домен игры и тот же origin
для отправки. `localhost`, `127.0.0.1`, `file://`, однофайловый экспорт и тесты
по умолчанию ничего не отправляют. ID сайта публичный; секретов в `dist` нет.

В настройках публичной игры есть переключатель «Статистика игры». Учитываются
Do Not Track, Global Privacy Control и `localStorage['umami.disabled']`.
Отключение не затрагивает сохранение. Наши события не включают поисковые строки,
содержимое сохранения, журнал, URL query/hash, реферер, имена, email или стек
ошибки. Umami сам определяет браузер/ОС и примерную страну по запросу; IP не
включается в игровые события. Веб-сервер сохраняет обычные логи посещений
независимо от аналитики; для пути коллектора access log отключён.

## Включение на VPS при публикации

Настройка подготовлена локально; сама по себе правка репозитория не запускает
сервисы на VPS. Не заменять текущую игру и соседние сайты без публикации по
[обычному порядку](deployment.md).

1. На VPS с Docker Engine и Compose v2 скопировать `deployment/analytics/`
   в `/srv/parus/analytics/`, не копируя локальные `.env` или базы данных.
2. Запустить `python3 /srv/parus/analytics/setup.py`. Скрипт создаёт секреты
   с правами `0600`, запускает Umami **3.5.0** и PostgreSQL, меняет стандартный
   пароль администратора и регистрирует сайт с ID из `analytics-config.js`.
   Повторный запуск сохраняет пароль и данные. Если администратор позже включил
   2FA или поменял пароль вручную, управлять им через панель.
3. Перенести блоки `/analytics/` из `deployment/parus.nginx.conf` в конфигурацию
   этого сайта; `nginx -t`, затем reload. Публичен только POST `/analytics/api/send`.
   Остальной Umami, включая админку, доступен только на `127.0.0.1:3100`.
4. Опубликовать проверенный релиз игры. Включить в него оба `analytics*.js` и
   изменённые модули. Сверить ID и домен в конфиге со значениями `setup.py`.
5. Открыть панель через SSH-туннель:

   ```sh
   ssh -N -L 3100:127.0.0.1:3100 root@165.232.99.124
   ```

   Затем [http://127.0.0.1:3100](http://127.0.0.1:3100), пользователь `admin`.
   Пароль — `UMAMI_ADMIN_PASSWORD` в приватном `/srv/parus/analytics/.env`.
   Скрипт не выводит пароль в журналы. Публичную ссылку отчёта он не создаёт.
6. Из отдельного профиля открыть публичную игру, карточку, выбрать тему,
   запустить и завершить полёт, перезагрузить страницу. В панели должны
   появиться события одного игрока и одной экспедиции, без повторного старта.
   Проверить отключение статистики. Не проверять отправку из личного сохранения.

Подготовка `.env` без запуска: `python3 setup.py --prepare-only`.
Проверка Compose без запуска: `docker compose config --quiet` из папки сервиса.
Не публиковать `.env`, не открывать порт 3100 наружу.

База находится в отдельном Docker volume и переживает обновление игры и
`docker compose down`. Команда `down -v` удалит статистику — не использовать
при обычном обслуживании. Перед обновлением Umami делать резервную копию:

```sh
cd /srv/parus/analytics
mkdir -p backups
docker compose exec -T db pg_dump -U umami umami > backups/umami.sql
```

Резервные копии хранить вне публичного `site`. Для отката подключения достаточно
выставить `enabled: false` в конфиге нового релиза; база статистики сохранится.
